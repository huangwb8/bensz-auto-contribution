# 项目绑定与安全追加修复计划

## 具体问题

新项目创建账本后再配置 Git 远程地址，下一条贡献记录就可能让账本失效。这相当于账本把联系地址当成永久编号：地址更新后，编号也变了。目前写入还会先报告成功，直到下一次核对才发现问题。

## 判断与目标

已通过五组合成 CLI 实验确认：添加 origin、修改 origin、移动目录触发标识变化，普通 commit 与同路径 git init 不触发。目标是让正常地址更新继续记录，让目录迁移具有明确操作与追加证据，并保证无效候选不会替换原账本。

## 改进方向

沿用现有 v2 格式和 genesis 的 root_hash，不改历史事件。所有内部写入入口显式传入账本当前项目绑定：路径一致时保留固定 root_hash，同时采集最新 remote、commit、branch 等上下文；路径不一致时拒绝普通写入，提示使用 `bac project rebind`。该显式命令只接收结构有效的账本，在新目录追加来源为 system 的 verification 事件，记录旧路径和新路径，表示工具完成重新绑定；不声明身份认证或用户贡献。

容器替换前调用完整验证器检查候选 ZIP、manifest 与事件链。任何错误都保留旧文件字节；warning 不阻止写入。低层构造器保留无绑定参数的兼容用法，但追加器拒绝不一致事件，绝不自动改写调用者的项目字段。

## 范围与顺序

先添加 origin 漂移、拒绝无效候选、目录迁移与旧事件不变的失败测试；再修改上下文采集、事件构造、CLI、repair 的内部追加和容器验证；最后更新中英文说明、教程、CHANGELOG 并审查差异。

## 兼容与安全边界

- 有效旧账本继续使用原始 root_hash，无需迁移。
- 目录复制与迁移无法仅凭本地路径证明属于同一项目，必须显式重绑定；这仍是声明式过程记录，不是身份真实性证明。
- 已混入多个 root_hash 的故障账本保持拒绝写入，不能只靠新增事件消除旧错误；不自动重算历史 hash，不操作外部账本。
- 锚定、配置、人类输入导入、repair 记录均沿用同一绑定逻辑；在可发现的绑定错误发生时先拒绝，再执行远程副作用或本地修复。
- 保留已有未提交发布文档变更，版本号保持原值；本次不发布或安装软件。

## 验收

添加／修改 origin 后所有本地追加入口及有效 receipt 导入均保持校验成功；旧 manifest 与旧事件原始内容不变；目录移动后普通写入不改文件，显式 rebind 后可继续写入；非法绑定、schema、hash、签名或来源事件均不能替换原文件；错误保留定位，tamper-evident 验证不放宽。运行定向测试和完整 Python 回归，并记录审查结果。

## 实施结果

已完成稳定绑定、显式目录重绑定和替换前完整校验，补齐全部内部构造调用，并在云端 link／anchor push 前检查既有账本与路径。新增回归先验证原实现失败，再完成实现；保留原验证器坏账本测试的全部断言，改由测试夹具直接构造非法历史。
