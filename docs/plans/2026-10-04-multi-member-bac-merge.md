# 多成员 BAC 合并优化计划

## 通俗解释：究竟发生了什么

**当前结论：项目尚未准备好安全合并多个成员的 BAC。** 已有能力可以保护一个账本的连续写入，但不能把 n 位成员各自保存的账本汇成完整、可验证的团队记录。

可以把成员的 BAC 理解为每个人的工作账本。甲记录需求讨论和程序开发，乙记录实验和分析，丙记录论文修改。团队发表论文时，需要把这些账本一起交给审阅者，既能看全团队过程，又能查回每条记录来自哪本账、由谁或什么产生。

现在，把几本账的内容直接接起来，会破坏它们原有的验证关系；只选一本账，则会遗漏其他人的过程。改进后，团队生成一个新的 `team.bac`：它保留各成员提交的原始账本，另附统一索引和合并记录。审阅者可以按成员、来源和成果浏览，发现问题后仍能回到原始记录。

这里的“合并”指汇聚过程证据。成员提交的账本可能同时包含 human、ai、tool、system 四类来源；账本由甲提交，不代表其中所有内容都由甲创作。

本计划状态为**待审核**。本次完成现状调查与方案设计，未实现合并功能，也未决定论文作者顺序或贡献比例。

## 专业判断：问题在哪里

### 当前能力与缺口

以下结论基于 2026-10-04 本地源码、文档、CLI 帮助与受控复现，不依赖旧架构计划中的设想。

| 检查项 | 当前能力 | 对团队场景的影响 |
|---|---|---|
| 合并入口 | CLI 提供 init、record、input、verify、repair、inspect、config、anchor、cloud，没有 merge | 无法接收多个 BAC 并产出合并报告 |
| 容器结构 | v2 ZIP 中保存一份 manifest 和一条连续事件序列 | 没有多账本清单、原账本快照或团队索引规范 |
| 哈希链 | 每条事件仅有一个 `prev_event_hash`，验证要求它等于上一条事件的 hash | 独立账本或共同历史后的分叉无法直接拼接 |
| 项目绑定 | `root_hash` 由本机项目绝对路径和 Git remote 计算，单账本要求该值不变 | 同一项目的不同机器、目录或 fork 可能得到不同绑定 |
| 成员识别 | actor 使用声明名称、种类和可选 session；输入记录默认 actor 为 human | 没有稳定成员映射，不能可靠地按团队成员汇总 |
| 引用关系 | 人类批准、AI 意图补充只能引用同一账本的前序事件 | 改写原链会影响已有引用；跨账本关系尚无规范 |
| 身份与可信时间 | 已有远程锚定 receipt；尚未实现贡献事件签名 | 有效 receipt 不等于成员身份真实，也不等于整个历史完整 |
| 阅读与界面 | inspect 面向单链；VS Code 查看器要求 v2 manifest 并拒绝非约定成员 | 新集合需要明确版本分派与兼容提示 |
| 并发和修复 | 日常追加有单账本锁和原子替换；repair 只处理受限机械性坏尾部 | 不能用于跨机器协作合并或贡献历史重写 |

核查入口：`src/bac/adapters/cli.py`、`src/bac/core/container.py`、`src/bac/core/schema.py`、`src/bac/storage/bac_file.py`、`src/bac/core/verify.py`、`src/bac/service/evidence.py`、`src/bac/service/event_builder.py`、`src/bac/core/intent.py`、`src/bac/report/inspect.py`、`softwares/vscode-plugin/src/ledger.ts`。

### 已验证的失败场景

在两个临时项目目录中分别初始化账本并追加人类需求事件：

- 两份原账本均无验证错误，只提示尚未锚定。
- 直接连接两份事件序列，验证报告为 fail，包含前序 hash 不匹配和项目 `root_hash` 改变。
- 删除第二份账本的 genesis 后再连接，仍然出现上述错误。

复现结果保存在 `.bensz-api/task-20261004-1725-multi-bac-merge/writing-plans/log/assessment.json`。这是现有规则的行为确认，不是新合并功能的验收。

### 为什么不能重算所有事件再串成一条链

重算前序 hash 会改变事件 hash，进而影响后续事件、人类批准引用、AI 理解引用和已经存在的远程锚定证据。它还会给原本并行发生的工作制造一个新的串行顺序。

因此建议保留原链，新增集合层。每本原账继续独立验证，团队层负责证明“本次收到了哪些账本、怎样建立索引、哪些声明仍缺证据”。

## 要达到什么目标

审核通过并实施后，团队能够：

- 汇聚 n 位成员的 v2 BAC，包含独立初始化、共享历史、复制后分叉和同一账本不同版本等情况。
- 得到一个可携带的 `.bac` 集合；所有输入保持原字节，合并过程可复核。
- 按提交成员、事件实际来源、文件和声明时间查看记录，同时保留原账本顺序。
- 查出重复提交、身份冲突、项目映射缺失、坏链、缺少成员材料和未经确认的贡献声明。
- 将汇总报告绑定到具体 Git commit、论文文件 hash 或其它最终成果版本，供团队人工讨论贡献说明。
- 后续成员继续工作时，可以生成新的集合版本，并保留上一版本与本次新增证据的关系。

本次实施范围不包括代码内容自动合并、论文作者排序、贡献百分比计算、组织账号权限系统、自动签发成员身份证明，以及通用分布式账本同步。事件数量和代码行数不能直接解释为学术贡献权重。

## 威胁模型：合并时要防止哪些误判

假设提交者可能误交、漏交或修改文件，合并操作者也可能选择性提交材料；成员设备时钟和自报身份均不天然可信。

| 风险 | 处理方式 | 仍存在的边界 |
|---|---|---|
| 修改原链或合并索引后伪装有效 | 逐原账验证、快照 hash、描述绑定和索引重建 | 有写权限者可重建整个未锚定集合，需要外部已保存摘要或可信 receipt 发现替换 |
| 漏交成员或使用较早账本 | 检查预期清单，保留版本关系与已知旧快照 | 从未观察过的新事件无法凭空发现 |
| 将他人或 AI 工作记到提交成员名下 | 提交关系与 actor、source_type 分开显示 | 声明成员代号本身不能证明现实身份 |
| 借合并改变历史顺序或批准关系 | 原链不变，跨链排序只作为展示 | 不提供全团队的可信真实发生顺序 |
| 恶意容器耗尽资源或越界访问 | 限制输入、解压和事件总量，拒绝路径逃逸与任意嵌套 | 超限材料需明确调整配置，不能无界读取 |

## 改进方向

### 保留原始账本，新增可独立识别的集合格式

新增 `bac.collection.v1` 容器，继续使用 `.bac` 后缀，通过 manifest 中的格式字段区别于已有 `bac.container.v2`。容器收纳原始 v2 BAC 快照、团队映射与成果绑定描述、可重建的统一索引，以及一份记录合并操作的 v2 审计账本。

成员原账本的 genesis、事件内容、hash、checkpoint 和 receipt 全部保持原样。集合层不提升原事件信任等级。汇聚工具生成的验证和统计记录属于 tool；集合初始化与 checkpoint 属于 system；AI 生成的说明属于 ai；人类审核只有真实发生并被宿主捕获后才属于 human。

对普通用户而言，交付的是一个团队文件，同时保留每个人的原始证据。

### 共享项目标识与成员映射

使用项目内低敏团队配置，例如 `docs/bac-team.json`，记录稳定 `project_id`、成员代号、预期成员清单、允许接收的账本绑定和目标成果。新团队共同采用项目标识；旧账本通过显式映射加入，原 `root_hash` 不修改。

项目映射须同时保留依据和声明状态：共同 Git 历史、项目配置或团队授权可作为依据；仅有相似项目名、相同 remote、相同文件路径或操作者指定的 ID，不足以证明来自同一项目。无 Git 的项目允许通过明确声明接收，但报告须显示“项目关联由声明提供”。缺少映射或存在冲突时，dry-run 输出问题并阻止正式生成。

区分三个概念：提交账本的成员、事件中的 actor 声明、event 的 source_type。成员代号不覆盖原 actor，更不能把该成员使用 AI 生成的内容改成 human。同名成员不自动合并；同一人的多个会话可显式关联。复制账本中的共享历史不自动归给每个复制者。

默认支持声明式成员信息，但明确显示“身份未验证”。成员身份认证是后续能力，不把当前远程锚定当作身份认证。

默认按团队配置要求提交完整成员材料，缺少必需成员时阻止正式生成。确需阶段性汇总时，显式选择允许部分材料，并把缺少的成员与“部分集合”状态写入描述和报告。

对普通用户而言，换电脑或 clone 到另一目录后仍能归入同一团队，而且不会把 AI 的工作记成某位成员手写。

### 去重、分叉和顺序必须可解释

输入先按稳定快照读取和验证，再建立索引：

- 相同原文件 hash 的重复输入只存一份快照，但保留提交关系。
- 共同历史中的完全相同事件可以在统一视图中只展示一次，保留所有原账本位置；比较完整事件内容，不能仅凭 event_id、摘要或时间去重。
- 同一逻辑账本存在前缀与扩展版本时保留版本关系；出现多个有效后继则显示分叉，保留各分支。
- 相同事件 ID 却内容不同，列为需处理的标识冲突；不静默挑选某一份。缺失引用和无效原链阻止正式合并。
- 同路径不同文件 hash 表示不同版本证据；不同的贡献声明表示待审阅事项。两者都不自动认定为代码冲突或造假。

统一视图保证各原链内部顺序和既有引用。跨链时间仅用于展示，标为“成员设备声明时间”；设备时钟不能证明真实先后。采用保持原链依赖的稳定排序和明确的同时间规则，相同输入与配置产生相同内容描述摘要。新合并记录有新时间和 ID，因此不承诺每次输出 ZIP 字节完全相同。

对普通用户而言，同一项公共历史不会被重复计数，并行工作也不会被错误描述成某人先后接手。

### 合并验证必须覆盖整个集合

验证分三层执行：原账本结构与哈希链、集合描述与快照对应关系、统一索引与原事件对应关系。索引是派生结果，能从快照重新计算并比较；不能只验证外壳就返回成功。

合并内容描述绑定每份原账本的文件 hash、genesis、head、事件数量、提交映射、成员清单、成果版本和排序／去重规则。其摘要写入合并审计事件，之后可使用现有锚定机制锚定该审计链。保持无循环依赖：被 hash 的内容描述不包含随后生成的审计链摘要。

原账本的 fail 阻止正式合并；warn 可以接收，但整体报告传播具体 warning，不因团队文件验证通过而隐藏未签名、未锚定或人类输入漏记问题。严格锚定策略分别说明原账本锚定要求与团队合并锚定要求；团队 receipt 不能替代成员历史的 receipt。

工具可以检测“缺少配置中要求的成员”或“与已保存快照相比发生截断”，但无法检测从未提交过的成员或事件。公钥来自账本自身时，验签只能证明与该 key 一致；需要可信机构身份时还须独立信任该 key。

对普通用户而言，验证报告会明确指出哪位成员的哪份材料存在问题，并保留尚未解决的证据缺口。

### 提供团队报告，辅助论文贡献讨论

扩展 inspect，按成员代号、来源和文件过滤，并导出结构化 JSON 与易读 Markdown。每条记录能定位到原账本快照和原 event_hash；报告显示成员贡献线索、AI／工具参与、人工批准和待确认项。

报告绑定目标论文文件 hash、Git commit 或其它成果摘要，同时区分“研发过程中的记录”和“已经核对纳入最终成果的证据”。只绑定论文版本，不代表已经证明每项研发工作被论文采用；缺少可验证关系时显示未核对，不自动计算署名或贡献份额。报告默认控制敏感字段，分享前提供预览；原始快照可能含历史路径等敏感信息，不能通过静默修改快照来脱敏。

第一阶段交付 CLI 与报告。VS Code 插件识别新格式并提供准确提示；团队可视化筛选和成员面板作为后续 UI 工作，不作为 CLI 交付的前置条件。

对普通用户而言，团队能拿着有来源定位的材料讨论论文贡献，而不是只看到缺乏证据的总分。

## 实施范围与顺序

| 阶段 | 要解决的主要问题 | 交付与完成条件 |
|---|---|---|
| 格式与边界 | 什么算同项目、谁提交、哪些证据需保留 | 集合规范、团队配置、威胁模型和受控样例；固定来源、版本与信任规则 |
| 合并核心 | 安全接收多份原链并构建集合 | dry-run、快照验证、去重／分叉／冲突报告、集合写入和完整验证；输入不变 |
| 团队报告 | 能否按成员复核并绑定最终成果 | inspect 过滤、JSON／Markdown 导出、成果绑定与未核对状态；三成员例子可完整回溯 |
| 兼容与交付 | 后续更新及已有用户如何使用 | 新旧格式分派、插件提示、文档、CHANGELOG、BAC 和完整回归验收 |

核心实现集中在 Python 的容器、存储、验证、合并服务、CLI 和报告模块；新增职责单独封装，复用原 v2 验证器。测试放在 `tests/`；插件识别和测试只放在 `softwares/vscode-plugin/`。不修改已有单账本追加规则来容纳多条链。

后续集合更新采用“上一集合 + 新账本快照 → 新输出文件”。旧快照与审计链前缀保留，新增一条合并记录；成员撤回或范围变化追加解释，不删除历史。首版仅支持这种显式版本更新，不自动同步目录或远端。相同描述的重复更新应返回 no-op。

## 如何确认完成

| 验收场景 | 必须看到的结果 |
|---|---|
| 三位成员研发并共同写论文 | 一个团队集合，三份原账可独立验证；按成员和四类来源浏览，报告绑定论文版本 |
| 同项目位于不同机器／clone 目录 | 经明确映射接收；原 root_hash 和事件均保持不变 |
| 非 Git 项目及错误项目混入 | 允许明确声明的关联并显示限度；缺映射或冲突时阻止生成 |
| 重复输入、共享历史、前缀版本 | 展示不重复计数，提交位置和版本关系不丢失 |
| 有效复制分叉、同 ID 不同内容 | 分叉保持两支；ID 冲突准确定位并阻止正式生成 |
| AI 生成和人类采纳 | AI 记录保持 ai，人类批准保持 human；提交成员不是统一创作者 |
| 批准引用和 AI 理解补充 | 原账本内关系全部保留，集合索引可回溯；不绕过原验证规则 |
| 并行事件、相同时间、时钟倒退 | 原链顺序稳定，跨链不宣称真实因果；交换输入顺序后描述摘要相同 |
| 篡改原链、替换快照、改团队映射或索引 | 逐层验证失败；指出原账本、事件或集合字段位置 |
| 已锚定原账与团队锚定 | 原 receipt 原样保留并验证；团队 receipt 只覆盖其绑定范围 |
| 缺少预期成员、旧版本或历史截断 | 可检查的缺口明确显示；不能把本地验证解释为全部成员历史完整 |
| 成员继续追加并重新汇聚 | 新输出保留旧快照、旧审计前缀和新增关系；重复更新 no-op |
| 损坏 ZIP、路径逃逸、超限与读取时文件变化 | 有界读取、拒绝不稳定快照；不解压执行成员记录的命令 |
| 输出中断、路径别名和写入竞争 | 已有输入与输出不损坏；输出不得覆盖输入或既有集合 |
| 旧 v2 与现有功能 | 全量 Python 回归通过；原 init／record／input／verify／repair／inspect／anchor 行为保留 |
| VS Code 打开集合 | 明确提示新格式及 CLI 阅读方法，不误显示单账本验证成功 |

所有涉及 hash、身份、锚定、时间顺序与审计数据的新增规则都配套自动化测试；再用三位虚构成员的完整研发到论文示例人工审核输出。计划不提前承诺具体通过数量，实施后记录真实测试证据。

## 风险与待确认事项

- **格式兼容：** 现有工具不能理解集合，因此新格式必须显式区别；新 CLI 继续支持旧 v2。旧 CLI 应拒绝新格式，不能把零条／部分事件当成功。旧插件保持拒绝，新插件给出说明。
- **容量：** 多份快照可能超过当前单账本 50 MiB 限制。集合设独立、有界且可配置的总压缩大小、累计解压量、原账本数量和总事件数；每份原账本仍遵守现有限制，不能无限递归嵌套集合。
- **声明真实性：** 有效 hash 链只能确认所提交数据的自洽性。成员身份、真实操作、历史完整性和最终成果采用范围须分别披露，不能因合并验证成功而一并认定。
- **隐私：** 保留原字节会保留其中已有的路径、声明名称或其它历史内容。需要公开脱敏版时，另产出明确标记的报告；不能称它与完整原账具有相同证据覆盖。
- **失败恢复：** 默认 dry-run，正式生成新文件前验证所有稳定输入；临时容器验证成功后原子落盘，禁止覆盖既有目标。失败时清理临时文件并保留原账本；并发创建同一目标只能有一个成功。
- **执行范围：** 建议先审核并实施 CLI 集合、完整验证和团队报告。成员签名、组织权限、团队查看器与自动同步在确有需求时另立计划。

## 技术补充（按需阅读）

为避免实现阶段对“合并”产生不同理解，建议固定以下接口语义，具体参数名在实现时统一核对 CLI 风格：

- `bac merge` 接收多个项目内输入路径、团队配置和新输出路径；默认只输出计划，显式 `--apply` 才生成集合，支持 JSON。
- `--base` 可指定上一集合，执行追加版本更新；成员输入限 v2 原账本，不接受任意嵌套集合。
- `bac --bac-file <集合路径> verify/inspect` 按格式分派；record、input、repair、config 和 anchor 直接操作集合时明确拒绝。团队审计链的锚定通过 merge 的专用选项调用既有核心机制，不暴露内部快照写入。
- 成员快照用内容摘要定位；事件索引使用“快照摘要 + 原序号 + 原 event_hash”，不依赖全局 event_id 唯一性。成员映射只增加提交关系，不改写原事件。
- 集合内容描述使用规范 JSON 计算摘要，列出项目／成员／成果、全部快照摘要、原 head／genesis／事件数、规则版本、索引摘要及前一集合关系；合并工具事件绑定该摘要。审计链摘要随后写入外层 manifest，避免循环 hash。
- 验证器从原快照重新检查描述及索引，逐账本输出状态，再输出整体状态和覆盖范围。集合不能被当成一条重新生成的贡献链。

审核重点：是否认可“原账本不变 + 团队集合”的方向，以及首版以 CLI／报告满足论文贡献审阅场景的范围。
