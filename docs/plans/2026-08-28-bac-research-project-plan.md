# BAC 严肃人机协作贡献溯源研究计划

## 研究定位

本项目不把 BAC 包装成“AI 生成比例检测器”，也不把哈希链误称为绝对不可篡改。建议将论文主题定位为：

> **面向科研、临床病例讨论和复杂软件工程等严肃场景的 Human–AI Contribution Provenance：用贡献状态机记录并验证人类意图、AI 工作、工具观察和最终授权。**

“严肃场景”不是按行业名称硬编码，而是按后果定义：任务需要事后解释谁提出了目标、谁设定了约束、谁选择或否决了方案、谁验证了结果、谁承担最终授权责任。简单一次性小应用不需要承担这类记录成本，可以作为低风险外部效度对照，而非主要应用场景。

本计划的核心不是证明“BAC 一定更好”，而是建立一个可证伪的评价框架，回答 BAC 在什么条件下比现有记录方式更有用、代价是什么、何时不值得使用。

## 研究主张与创新点

### 主张一：把贡献从百分比改写为可验证事件图

Git 主要描述提交者、快照和 diff；普通操作日志描述命令或系统活动；AI 检测器描述产物像不像模型生成。它们都难以同时表示“人类提出问题—设定约束—选择路径—评价失败—最终授权”的认知链条。BAC 的研究创新应表述为一种**贡献状态机/事件本体**：来源（human、ai、tool、system）与信任等级分离，声明事件与观察事件分离，批准不改写创作来源。

### 主张二：提出“恢复贡献边界”而非“检测 AI”作为评价任务

主要终点不再是检测器准确率，而是隐藏真值下的关键事件召回、来源归因、因果顺序恢复、责任边界解释一致性和审计者校准。这个评价任务可以把 BAC 与 Git、普通日志、检测器放进同一实验，而不会把不同工具强行当成同一种产品。

### 主张三：把完整性、真实性、语义和隐私分开测量

哈希链通过验证只能说明记录在写入后未被轻易改动，不能证明写入者一开始没有撒谎，也不能证明每个真实动作都被记录。因此论文必须分别报告：

- **完整性**：插入、删除、重排、尾部截断和重复条目能否被发现；
- **来源真实性**：事件来源是否符合隐藏真值和工具观测；
- **语义充分性**：审计者是否能恢复决策与授权；
- **隐私/成本**：脱敏后泄露多少、记录负担多大。

### 主张四：验证 BAC 的意外反馈价值

自动记录低敏人类输入不仅是归因证据，也可能把零散反馈组织成可分析的过程数据，帮助改进用户流程、agent skill 和大型项目复盘。该方向应作为独立因果实验，不把“日志更多”直接等同于“流程更好”。

## 科学问题与可证伪假设

### Q1：BAC 是否更能恢复真实贡献边界？（主问题）

**H1**：在具有隐藏真值的人机协作任务中，BAC 条件的关键事件召回率、四类来源宏平均 F1、事件关系恢复准确率和解释一致性，高于 Git、Git+普通日志和单独 AI 检测器；若预注册的等效性检验显示差异小于最小实际重要差异，则 H1 不成立。

关键预测是：BAC 对“人类约束、方案选择、否决、审阅、批准”等高层事件的增益大于对代码行级来源的增益。若 Git+普通日志在这些指标上同样好，BAC 的创新应收缩为格式整合，而不是完整方法学优势。

### Q2：BAC 的 tamper-evident 与语义校验是否提高对抗审计能力？

**H2**：在来源漂白、事件删尾、重排、复制、AI 活动但无 human input provenance 等攻击下，BAC 的风险发现率和置信度校准优于无哈希链的普通日志；若 BAC 误报显著增加、或攻击成功率不下降，则 H2 不成立。

注意：该假设只检验“篡改可发现”和“语义矛盾可提示”，不声称 BAC 能阻止有写权限者从一开始写入虚假事件。

### Q3：记录人类输入是否改善反馈组织与复盘？

**H3**：在相同任务和 AI 工具下，启用 `bac input record` 并以事件视图组织反馈的团队，在反馈可执行性、问题召回、下一轮流程改进质量和复盘责任边界清晰度上优于仅保留聊天/Git 的团队；若改进完全由额外投入时间解释，或在盲评中不可复现，则 H3 不成立。

### Q4：核心本体能否跨严肃领域迁移？

**H4**：Human、AI、Tool、System 四类来源以及意图、生成、观察、审阅、批准、验证等核心事件，在软件开发、科研分析和临床病例讨论中都能保持预设的编码一致性和审计可理解性；若每个领域都必须重写大部分本体，或跨领域一致性低于预设阈值，则 H4 不成立。

## 总体研究设计

采用“真实账本语料观察 → 隐藏真值基准 → 随机审计实验 → 反馈/复盘用户研究 → 跨领域复制”的混合方法路线。先用已有 `contribution.bac` 验证事件分布和数据字典，再用可控任务回答因果问题，最后用访谈解释为什么某些事件对人有用或造成负担。

### 对照条件

| 条件 | 可见材料 | 用途 |
|---|---|---|
| A：产物 | 最终文件/分析结果与时间戳 | 最低信息基线 |
| B：Git | commit、作者、时间、diff | 传统版本控制基线 |
| C：Git+日志 | Git 加命令/CI/IDE/聊天摘要 | 普通 provenance 基线 |
| D：检测器 | 内容检测器或水印结果 | 产物来源交叉证据，不当作完整过程记录 |
| E：BAC | 完整事件、四类来源、证据、验证状态 | 主干干预 |
| F：BAC 消融 | 去除人类输入、语义校验或哈希链 | 定位 BAC 哪个组件产生增益 |

所有条件使用同一任务、同一隐藏真值和同一时间窗口；只改变审计者可见证据，避免把任务难度差异误当作工具效果。

## 研究包与实验协议

### WP0：已有 BAC 语料的描述性研究

**目标**：回答 BAC 在真实实践项目中究竟记录了什么，先把“设计上应该记录”与“实际上记录”分开。

**数据**：以项目授权的 `contribution.bac` 及后续合作项目账本为单位；不得把完整私有 prompt、密钥或无关个人信息导入数据集。每个账本只保留脱敏后的事件元数据、事件类型、来源、信任等级、时间间隔、文件/命令摘要长度、验证状态和是否有人类输入 provenance。

**分析**：

1. 统计事件类型和来源构成、每个任务的状态机覆盖率、AI 事件与 human 事件的比例、测试/批准事件缺口。
2. 计算事件链长度、平均相邻事件间隔、重复/跳跃/验证失败率和脱敏比例。
3. 对账本做过程挖掘：常见路径是否为 `human_instruction → ai_generation → file_change → test_result → human_approval`，哪些路径在真实项目中断裂。
4. 将“人类输入事件缺失”“AI 活动但没有人类输入证据”“来源语义矛盾”作为风险表型，而不是自动判定违规。

**产出**：数据字典、事件覆盖率报告、匿名化基准任务抽样框架。该研究只能给出生态描述，不能单独证明 BAC 有效。

### WP1：隐藏真值贡献恢复基准

**任务集**：至少三类复杂任务，每类包含低、中、高风险版本：

- 软件：跨文件功能实现、重构、故障修复与测试；
- 科研：从给定数据和分析目标选择方法、解释冲突结果、生成可复现分析；
- 临床模拟：基于脱敏病例资料形成鉴别问题、检查计划和团队授权记录（仅研究模拟，不替代医疗建议）。

**真值记录**：由实验平台在事件发生时记录人类消息 hash/低敏摘要、AI 计划与生成、工具命令和返回、文件 diff、参与者手工编辑、审阅理由和最终批准。人工编码员独立复核，并保存不可供审计者查看的“真值包”。

**证据视图生成**：从同一真值包生成 A–F 条件；对 BAC 额外生成合法账本、删尾/重排/来源漂白/缺失人类输入/脱敏增强版本。攻击变体必须由脚本生成并保留变换日志，不能手工挑选有利样本。

**主要终点**：关键事件召回率、来源宏平均 F1、关系恢复准确率和证据条件间差值。

### WP2：盲法审计者定量实验

**参与者**：软件开发者、科研人员/研究生、临床或治理审阅者三类；先做 pilot，再根据主要终点的方差和最小重要差异进行功效计算。正式研究前冻结纳入标准、样本量、排除规则和分析代码。

**随机化**：按参与者经验分层；任务和证据条件用拉丁方或平衡不完全区组随机，避免同一参与者反复看到同一任务的学习效应。审计者不知道真值和生成条件。

**任务**：给出若干账本/证据包，要求审计者回答：谁提出了目标、谁设定约束、AI 做了什么、工具观察到什么、谁批准了什么、是否存在风险以及依据是什么。

**测量**：

- 事实恢复：事件级 precision/recall/F1；
- 来源与责任边界：human/ai/tool/system 归因准确率、误归因率；
- 因果解释：顺序、审批指向、文件上下文和测试证据的正确率；
- 风险判断：攻击发现率、误报率、Brier 分数/期望校准误差；
- 可用性：完成时间、认知负担量表、解释长度、主观信任与信任校准。

**统计**：以参与者和任务为随机效应的混合效应模型；主要比较 E vs B/C，并报告 E vs F 的组件增益。比例指标同时报告绝对差和 95% CI；多重主要终点采用预先指定的层级检验或 BH 校正。缺失值、放弃任务和异常长时间不能事后删除，需按预注册规则处理并做敏感性分析。

### WP3：来源漂白与完整性对抗实验

构造四类攻击：

1. **来源漂白**：把 `ai_generation` 或 AI 驱动的 `file_change` 标为 human；
2. **链破坏**：删除、重排、复制事件或修改 payload；
3. **证据删减**：删除人类输入、测试失败或批准事件；
4. **隐私压力**：比较完整 prompt、低敏摘要和仅 hash 三种披露粒度。

记录验证器是否拒绝/警告、审计者是否发现、发现所需时间和误报。把“验证通过”与“语义上足够”分开统计：前者是系统属性，后者是人的判断结果。

### WP4：反馈组织与项目复盘实验

采用 2×2 设计：

- 输入记录：关闭 vs 自动 `bac input record`；
- 复盘界面：仅聊天/Git vs 按 BAC 事件状态机聚合。

参与者完成一组连续任务，第二轮允许根据第一轮复盘改进 prompt、agent skill 或团队流程。盲评者根据任务结果和过程材料评分：反馈是否具体可执行、失败原因是否被正确定位、下一轮是否避免同类错误、责任边界是否清晰。另做半结构访谈，追问哪些事件帮助了判断、哪些摘要造成误解、何种记录粒度被认为过度。

该实验应控制额外时间：记录自动化的时间成本单列，复盘材料阅读时长作为协变量；否则无法区分“BAC 带来的结构化价值”和“参与者投入更多时间”。

### WP5：跨领域可迁移性与最小本体

将 WP1 的事件代码本体交给各领域专家独立编码。比较：核心事件保留率、领域扩展字段比例、编码者一致性、审计者理解时间和对关键责任问题的回答准确率。若领域差异很大，应把 BAC 贡献表述为“可扩展框架”，不要宣称一个固定 schema 能覆盖所有专业规范。

## 指标定义

### 贡献恢复

设隐藏真值事件集合为 `T`，审计者恢复集合为 `R`。关键事件召回率为 `|T∩R|/|T|`，来源宏平均 F1 对四类来源分别计算后取平均。关系恢复需同时满足事件节点和关系边正确；不能只因事件名称相似就算正确。

### 审计效用

对每个审计任务记录正确性、完成时间和解释可读性；可报告单位时间正确恢复数，但不能用它替代准确率。风险判断同时报告灵敏度、特异度、误报率和校准曲线。

### 记录负担与隐私

记录负担 = 自动记录 CPU/墙钟时间、写入失败率、账本字节数/任务时长、用户额外操作数和中断次数。隐私指标包括敏感 token 召回率、人工可识别性评分、脱敏前后审计性能差值。不得把“保存完整 prompt”作为默认高分方案。

## 质量控制与可复现性

- 预注册主要问题、假设、终点、最小重要差异、随机化、排除和统计模型。
- 真值包、攻击生成器、评分 rubric、匿名化脚本和分析代码版本化；原始私密材料不进入公开仓库。
- 至少两名编码员独立标注关键事件和关系，计算一致性，分歧由第三名裁决并保留理由。
- 审计者、编码员和分析者尽量盲于证据条件；自动生成视图时记录脚本版本和输入 hash。
- 任何 BAC 验证失败都保存可解释错误类型；把容器完整性测试、语义规则测试和脱敏测试分开。
- 对不同任务难度、参与者经验、领域和记录粒度做预先指定的亚组与敏感性分析。

## BAC 为科研所需的最小扩展

不建议为了论文一次性重写格式。优先增加可导出但默认脱敏的研究字段：`task_id`、`session_id`、`message_index`、`event_relation`、`ground_truth_ref`（仅真值包内部）、`view_condition` 和 `redaction_policy_version`。正式账本不写入真值或完整私有 prompt；研究导出器生成去标识化分析表。

同时提供稳定的 `bac inspect --json`、验证错误码、事件类型统计和审计视图导出，确保 A–F 对照条件可以由同一份原始真值程序化生成。

## 分阶段实施路线

### 阶段一：问题冻结与语料盘点（第 1–2 个月）

完成伦理/隐私评估、数据字典、WP0 语料统计、候选任务和预注册草案；补做针对 contribution provenance、human agency、audit log、software provenance、AI-assisted work 的系统查新。查新结果只用于调整新颖性表述，不用来替代实证。

### 阶段二：基准与工具链（第 3–4 个月）

实现真值采集器、A–F 视图生成器、攻击生成器、匿名化和评分工具；用内部小样本检查事件覆盖、哈希链验证和脱敏边界。

### 阶段三：pilot 与正式审计实验（第 5–7 个月）

先做 pilot 估计方差和任务时长，再冻结样本量与分析脚本；开展 WP2/WP3，形成主论文数据。

### 阶段四：反馈/复盘与跨域复制（第 8–10 个月）

开展 WP4、WP5，访谈并分析记录负担、流程改进和迁移边界。

### 阶段五：论文与开放材料（第 11–12 个月）

发布匿名化事件 schema、视图生成器、攻击脚本、评分 rubric 和可复现分析；论文中同时报告正结果、无差异结果、失败案例和适用边界。

## 最小可发表版本

资源有限时，先完成一个软件开发场景的 WP1–WP3：20–30 个高保真任务、三种主要基线（Git、Git+日志、BAC）、四类攻击、盲法审计者实验和完整成本/隐私报告。不要在没有数据的情况下声称“适用于科研和临床”；跨领域只作为后续研究方向。

## 预期成果

1. 一篇主论文：贡献事件恢复基准、BAC 与 Git/日志/检测器的对照及对抗审计结果。
2. 一篇方法/系统论文：最小贡献事件本体、脱敏策略、验证语义和跨工具映射。
3. 一篇用户研究或应用论文：人类输入 provenance 对反馈组织和大型项目复盘的影响。
4. 开放但去标识化的 benchmark、视图生成器、攻击脚本、分析代码和研究协议。

## 风险、边界与停止规则

- **记录不等于真实贡献**：BAC 只能提供可复核过程证据，不能自动裁定作者、版权、法律责任或学术署名。
- **样例账本偏差**：现有项目由开发者自记录，不能代表所有用户；WP0 只做描述，WP1 才承担因果比较。
- **检测器比较不对称**：检测器只观察产物来源，必须作为补充基线并明确其能力边界。
- **隐私与伦理**：科研和临床材料必须脱敏、最小披露、分级访问；不收集完整私有 prompt、密钥或不必要的个人数据。
- **停止/收缩规则**：若 BAC 相对 Git+日志在主终点不具实际重要差异，停止“全面优于现有工具”的叙事，转而报告其在高层决策恢复、攻击发现或复盘组织中的局部优势；若记录成本超过预设阈值，则优先研究更低粒度的摘要/哈希方案。
