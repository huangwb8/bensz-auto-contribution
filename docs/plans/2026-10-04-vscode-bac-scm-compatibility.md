# VS Code 源代码管理打开 BAC 的兼容性优化计划

## 通俗解释：究竟发生了什么

**可以通过插件源码优化解决。** 现在从“源代码管理”点击更新过的 `.bac`，VS Code 要同时打开修改前和修改后的账本，但插件只允许打开本地文件，遇到 Git 保存的旧版本就拒绝打开，导致整个比较页报错。

这相当于查看账本时，既要翻开桌上的新版，也要取出档案里的旧版。桌上的账本对应工作区文件，档案里的账本对应 Git 版本；当前插件只认前一种入口。优化后，点击同一条变更，左右两侧能分别显示对应版本的贡献记录，并明确标注版本来源。

## 专业判断：问题在哪里

### 已确认的证据

- `softwares/vscode-plugin/package.json` 将 `bac.viewer` 注册为 `.bac` 的默认自定义编辑器，因此普通文件打开和 Git 差异打开都会进入插件。
- `src/extension.ts` 的 `Viewer.openCustomDocument` 明确拒绝所有非 `file:` URI（URI 是 VS Code 用来定位文件或历史版本的地址），包括源代码管理使用的 `git:` 地址。
- 本机 VS Code 日志在 **2026-10-04 13:05:23** 记录了“请从资源管理器打开本地 .bac；Git 版本比较请使用 BAC 比较按钮。”，调用栈指向已安装插件的 `Viewer.openCustomDocument`。这与截图中的原生编辑器错误、源码中的拒绝条件一致。日志对应插件 `0.1.0`，当前源码 `0.1.1` 仍保留相同限制。
- 本机 VS Code `1.140.0` 的 Git 扩展通过 `vscode.diff` 打开两个版本，并注册了只读的 `git:` 文件系统；其 `readFile` 返回二进制数据。BAC 是 ZIP 容器，需要保留这些原始字节才能正确解析。
- 本机 VS Code 对没有专用差异实现的自定义编辑器，会分别打开左右两个查看器。现有稳定类型接口只有普通自定义编辑器入口；专用 `customEditorDiffs` 在本机实现中仍受提议 API 开关控制。

**根因判断：** 默认编辑器接管了 Git 差异入口，但文档打开入口只支持本地资源。现有读取函数已经使用 `workspace.fs.stat/readFile`，因此可利用 Git 文件系统扩展读取能力；仅删除拒绝条件仍不足以完成修复，因为文件监听、版本标识、关联文件操作和验证都依赖当前的本地文件假设。

现有核心测试覆盖了容器解析和事件比较，界面测试覆盖了插件内部比较按钮与代码 diff，尚未覆盖从源代码管理点击 `.bac` 的真实入口。

## 要达到什么目标

- 直接点击源代码管理中的 BAC 变更，左右账本正常加载，能够阅读记录、筛选来源和查看详情。
- 工作区、暂存区（准备提交的版本）和指定历史版本有清楚的身份标识；每侧显示该地址实际指向的内容。
- 缺少某个版本时显示明确的空侧说明；无法读取或内容损坏时显示插件内的错误和恢复提示。
- 普通资源管理器打开、现有事件比较、事件 JSON diff、关联代码 diff 和完整验证继续可用。

诊断阶段交付了本计划；本次已完成下述实现与验收。实施限于插件兼容性及其测试、说明文档，不改变 BAC 格式、历史事件、签名规则或版本号，不包含发布和本机安装。

## 改进方向

### 让查看器识别 Git 保存的账本

将文档来源明确分为本地文件和 Git 版本。对可信工作区中的 Git 资源，激活内置 Git 扩展后，通过只读文件系统读取原始字节，再复用现有 `readLedger`；保留已有容器大小、解压大小和结构限制。

优先让内置 Git 提供器解释历史和暂存区地址，避免自行把特殊版本标记一律转换成 HEAD。对其它协议、格式异常的地址、跨项目路径和不支持的资源返回明确提示，不任意扩大访问权限。读取失败时不偷偷替换成工作区文件。

用户看到的变化：旧版和新版都能打开，而且不会出现两边实际显示同一份本地账本的情况。

### 适配原生左右比较的文档生命周期

沿用 VS Code 原生左右比较与现有只读查看器，分别维护两侧的加载、筛选、详情和验证状态。核对是否需要启用 `supportsMultipleEditorsPerDocument`，确保已经打开的工作区查看器不会被差异页抢占，关闭一侧也不会释放另一侧的状态。

来源信息应保留原始资源 URI，并单独记录受约束的项目内本地路径和版本标签。文件标题和状态区域应区分工作区、暂存区及历史版本。普通文件继续监听磁盘；暂存区变化从 Git 状态更新触发重新读取；固定提交按固定版本展示。异步读取结果仍受现有 generation 检查约束，避免旧请求覆盖新状态，并在关闭时释放监听器。

稳定 API 下，左右分别展示时间线可实现本次“正常显示”的目标。事件级新增、修改、删除和重排仍使用现有 BAC 比较入口。首轮不引入提议 API 来实现自动联动的专用差异界面。

用户看到的变化：从源代码管理打开时有正常的左右账本，版本身份明确，刷新、分屏和关闭不会串用状态。

### 把文件操作和验证绑定到实际版本

历史侧的关联文件操作只能访问对应仓库内经路径校验的文件，不能将 `git:` 地址直接当成本地路径。现有“与 HEAD 比较”命令继续明确标注 HEAD → 工作区；若增加暂存区入口，则显式区分 HEAD → 暂存区与暂存区 → 工作区，避免从暂存项打开后误报为其它比较。

完整验证继续使用私有临时快照。验证历史侧时，快照来自该侧的 Git 字节；报告与该份快照的摘要、事件数量和 head 绑定。工作区或暂存区更新后，清除对应侧的旧验证结果，不能借用另一侧的“通过”。未执行验证时保持“未验证”，正常解析不代表身份可信或历史完整。

新增、删除或无首次提交导致某侧不存在时，依据 Git 状态或明确的不存在结果显示空侧，不将所有读取错误视为“没有记录”；存在但损坏、权限受限或 Git 不可用应保留错误原因。恢复提示和新增版本标签同时提供英文及简体中文。

用户看到的变化：比较和验证有准确的版本含义，缺少历史与账本损坏会得到不同提示。

## 实施范围与顺序

1. 在独立扩展宿主与临时 Git 仓库中复现真实源代码管理点击，记录两侧 URI 和打开失败的证据，建立针对该入口的回归场景。
2. 扩展文档来源与读取逻辑，接入 Git 原始字节，适配左右查看器及版本标签、刷新和释放行为。
3. 校正历史侧关联文件与验证上下文，处理缺失版本和加载错误，保留现有只读和工作区信任约束。
4. 运行自动化与真实点击验收，更新插件中英文 README、`CHANGELOG.md` 与 BAC，再打包并检查 VSIX 供后续发布使用。

实现、界面资源、构建脚本与测试统一放在 `softwares/vscode-plugin`。主要涉及 `src/extension.ts`、来源处理所需的最小辅助模块、`src/i18n.ts`、`media/`、`test/` 和 `scripts/test-vscode.mjs`；确有注册项变化时才调整 `package.json`。

## 风险与安全边界

- 内置 Git 文件系统会解释其特殊版本地址，且可能受仓库配置的文本转换影响；需确认取得的是可解析的 BAC 容器。若被转换，评估用现有受限 `git cat-file` 路径获取原始 blob，并对路径、版本和大小严格校验，不能使用文本解码再编码还原 ZIP。
- Git 读取和验证遵守现有可信工作区要求，不自动执行账本事件中的命令，不联网、不上传账本或截图，不新增写入账本的查看器功能。
- 两侧可能含大账本，沿用读取上限并关注重复解析的内存成本；不为此预先引入缓存框架。
- BAC 的性质仍为 tamper-evident（修改可被发现）。可显示、可比较和本地验证通过都不等于身份真实性、贡献完整性或最终署名证明。

### 实现方案的调整与安全边界

- 检查内置 Git 的实际实现后发现 `buffer` 调用 `git show --textconv`，因此采用计划中允许的受限 `git cat-file` 原始 blob 方案。仓库和特殊 ref 的含义仍由内置 Git API 的项目状态约束；不用文本解码还原 ZIP，也不执行 textconv。
- Git URI 只允许空 ref、`~`、HEAD、完整对象 ID，以及 `~1`–`~3`／`:1`–`:3`；其它 ref、子模块 diff、路径不一致或项目外资源返回插件内错误。读取失败不回退为工作区文件。
- 原生 Git 在新增／删除时可能只打开已有版本；按真实入口验收其已有侧。另外直接打开缺失版本验证“版本不存在”提示。原生修改与暂存修改入口仍由 VS Code 打开两侧查看器；未使用提议 API。
- 内部事件比较继续明确使用 HEAD／暂存区／工作区范围，不改变历史侧的时间线与验证来源。工作区查看、事件 JSON diff、代码 diff、语言切换和既有验证功能保持可用。
- 更新监听先检查原始摘要与来源，避免无关 Git 状态或重复文件通知使验证误失效。关闭期间的异步初始化和旧读取结果受生命周期／generation 约束。
- 仅验证账本来源的快照，不重建整个历史项目，也不将解析或验证通过解释为身份真实性、历史完整性或最终署名证明。四类来源与 BAC 格式、签名规则保持原义。
